## 3. 发布状态机与不变量（设计已批准，功能待实现）

为便于后续数据库及 API 实测，将状态分为：

- **未发布**：没有已发布版本引用，`releaseGeneration=0` 是未发布状态的批准初始值；编辑 head 可以有多个版本，但 Runtime 不应自动使用任何编辑快照。
- **已发布**：指针指向本工程不可变快照，`releasedRevision` 与 `releasedContentHash` 一致，当前代次对应一条已提交成功事件。
- **成功再发布**：只有已批准的全部门禁都通过且成功事务提交，才增加一个发布代次和一个成功事件。编辑 head 与已发布指针可以不同。
- **成功回滚**：切换到本工程历史上曾正式发布过的版本，发布代次仍严格增加；编辑 head 不回退，不修改旧事件与历史版本。
- **受控失败**：401/403/404（按工程不可枚举政策）、409、快照损坏、资源失效、事务失败、幂等冲突均不得推进发布代次或部分提交事件。

**不变量 I-01**：一次成功提交的指针、代次和成功事件必须原子一致，不得仅有其一。

**不变量 I-02**：任意请求的目标版本、事件引用、租户与工程 ID 必须形成同一租户/工程内的闭包；不能以裸 `projectId` 在跨租户维度索引。

**不变量 I-03**：发布和回滚不修改 `headRevision`、已保存快照、React/Vue 画布、CAS 编辑基线和 IndexedDB 草稿。

**不变量 I-04**：旧 `expectedReleaseGeneration` 在任何后续成功发布/回滚后都不能再次提交，即使 `releasedRevision` 回到原数值（ABA）。

**不变量 I-05**：失败请求不得向 Runtime 报告新发布，不能通过旧报告的 `passed` 字段绕过事务内授权与重新预检。

**不变量 I-06**：工业侧异常仅允许可见、受控的只读降级；不接受客户端直连 PLC/DCS 或隐含写设备指令。

## 4. 分阶段负向测试矩阵（部分由 C1 覆盖，整体未完成）

下面的目标测试必须在**本机显式隔离**的 `adui_scada_test` PostgreSQL 与真实受控 BFF/HTTP 环境中建立随机专用租户/工程；对生产库或既有业务工程不得做写入或故障注入。C1 已通过真实 PostgreSQL 与 HTTP 测试覆盖其中一部分发布事务场景，但 T-01～T-22 是整体架构验收义务，不能因部分用例通过而全部标记完成。测试通过仅证明被测阶段，不代表工业现场发布许可。

| 用例 | 故障、并发或攻击输入                                     | 预期不变量 / 可观测结果                              |
| ---- | -------------------------------------------------------- | ---------------------------------------------------- |
| T-01 | 未认证主体调用未来发布命令                               | 401；零发布事件、零指针变更                          |
| T-02 | 仅有 `version:append`、没有 `release:publish`            | 默认拒绝；保存权限不能升级为发布权限                 |
| T-03 | 无权主体猜测另一租户的工程 ID                            | 资源不可枚举；零跨租户读取/写入                      |
| T-04 | 请求中客户端提交工程正文、用户 ID 或快照 hash            | 受控拒绝额外字段；仅以服务端已保存快照和可信主体为准 |
| T-05 | 版本已由另一主体推进，旧 `expectedHeadRevision` 发起发布 | 409；旧发布指针与成功事件不变                        |
| T-06 | 并发两主体从相同 `expectedReleaseGeneration` 发布        | 最多一个提交，其余返回冲突；代次无丢失               |
| T-07 | 请求在锁等待期间被撤销 `release:publish`                 | 锁内再验权，撤权后不可提交                           |
| T-08 | 快照元数据的 SHA-256 与实际工程正文不符                  | 拒绝发布；不写指针或成功事件                         |
| T-09 | 历史快照格式损坏或静态 SVG 兼容性失败                    | 拒绝发布；不能依赖先前 GET 预检报告                  |
| T-10 | 发布事件插入失败                                         | PostgreSQL 回滚；指针、代次均不变                    |
| T-11 | 指针更新或 CAS 写入失败                                  | PostgreSQL 回滚；不得留下孤立成功事件                |
| T-12 | 同幂等键同语义请求在网络超时后重复                       | 只返回第一次已提交结果，不新增代次或事件             |
| T-13 | 同幂等键携带不同目标或期望代次                           | 受控冲突；无额外事件                                 |
| T-14 | 发布 A → 发布 B → 回滚 A → 使用旧代次发布 B              | 旧代次 409；验证 ABA 不会覆盖新指针                  |
| T-15 | 回滚到本工程未曾发布但已保存的版本                       | 拒绝；编辑历史不能冒充发布历史                       |
| T-16 | 回滚到另一租户或另一工程的历史发布版本                   | 拒绝；不泄露目标是否存在                             |
| T-17 | 曾发布快照已损坏、Tag 绑定或运行时资源不再兼容           | 回滚 fail-closed；不因旧事件存在而跳过复核           |
| T-18 | 生产 Runtime 读到发布事务尚未提交的中间状态              | 只能读取原完整版本或新完整版本，不能读取部分切换     |
| T-19 | 已发布指针无效或不存在、DB 暂不可用、Tag 质量 BAD/STALE  | 明确告警/受控降级，不自动回落编辑 head 或伪造 GOOD   |
| T-20 | 会话过期、CSRF 错误、跨站 Origin 或非法 Fetch Metadata   | 受控拒绝；不允许发布状态写入                         |
| T-21 | 成功提交后网络回包迟到或丢失，客户端重新发送旧请求       | 幂等重查结果，不产生第二个事件；旧代次不被重放       |
| T-22 | 数据库并发死锁、事务超时或断连                           | 旧发布指针保持可验证，连接与锁释放，不留半写状态     |

T-01～T-22 是跨发布、回滚和 Runtime 的整体验收义务。C1 已真实验证发布命令的输入白名单、独立 ACL、快照摘要、静态兼容性拒绝、双 CAS 并发、幂等重试、会话/ACL 锁竞争、事件与指针原子提交及 HTTP Cookie/CSRF/Origin 路径；并不意味着 T-01～T-22 全部完成。回滚、Runtime 读者、运行时故障恢复、生产审批和工业安全仍需后续阶段独立验证。

## 2026-11-19 · 第三十五批 D1 服务端只读发布读取候选

D1 候选新增 `GET /api/v1/projects/:projectId/releases/current`，权限为独立 `release:read`，默认拒绝，不从 `project:read`、`version:read` 或发布写权限继承，也不在工程创建时自动授予。响应使用 `Cache-Control: no-store`，区分 `UNRELEASED` 与 `RELEASED`；已发布状态返回指针修订/摘要/代次、最后事件信息及不可变快照，不暴露编辑 head。

`PrismaProjectReleaseStore.readCurrent` 在同一只读事务中锁定工程身份（只选择 `project_id`，不读取 `head_revision`）、有效会话/主体、ACL、发布状态、不可变版本和最后发布事件；重新验证 SHA-256、快照元数据、最后事件与发布指针。数据库缺少状态行、事件不一致或快照校验失败均不返回快照正文。D1 候选尚未执行隔离 PostgreSQL 迁移/测试、Windows `vp check`、单测、HTTP E2E、`docs:check` 或完整 `ready`。
