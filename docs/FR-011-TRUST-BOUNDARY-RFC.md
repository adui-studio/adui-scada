- 关联需求：FR-004、FR-009、FR-010、FR-011、FR-014

## 一、已知事实与信任边界

- `TagStore.apply` 以逐 Tag **严格递增**的 `sequence` 接受更新，不要求连续；`classifyOrderedNumericAlarmSample` 同样只检查递增与服务端时间不回退。不能仅由 `5 → 7` 推导丢包或无损。
- `AlarmSubscriptionAdapter` 的 `onChange(change, sourceVerified)` 接收调用方给出的布尔值，不鉴别签发者；`generation` 是本地会话代次，不是身份凭据。
- Core 有 GOOD/有限数值、明确时区、公历日期、00–23 小时、最多毫秒小数秒、新鲜度与代次等**候选防护**，但不提供可信身份、服务端报警持久化及确认授权。
- 当前演示 SSE/离线模式不能证明现场采集可信。浏览器、React/Vue、Tauri 不得直接连接 PLC/DCS，不得开放通用设备写入。

**拟议边界（尚未批准）：**

```text
只读模拟数据源／未来受控工业网关
    │ 采集端身份和 Tag 范围验证（拟议）
    ▼
NestJS 可信接入边界（默认关闭）
    │ 服务端赋值时间、接入会话、序列域、缺口状态
    ▼
只读规范化 Tag 流 → Core 候选状态机
    │ 后续独立审查：规则、报警事件事务及审计
    ▼
Vue / React / Tauri 只读订阅（非可信身份签发者）
```

## 二、供审查的建议选项（不是已生效的架构契约）

| 议题     | 建议方向                                                                                                                                             | 必须由维护者确认的条件                                                        |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 入口身份 | 仅由受控网关或隔离模拟服务通过服务端认证；身份绑定可访问的工程、数据源及 Tag 白名单；浏览器传入的 `sourceVerified` 永不授信                          | 认证机制、凭据轮换、撤销、进程拓扑及部署运维                                  |
| 时间归属 | 区分原始 `sourceTimestamp` 与可信服务端接收时间；仅可信服务端赋予报警候选使用的 `serverTimestamp`，要求明确 UTC 和毫秒表示；记录原始精度，不静默截断 | 时钟同步基线、跨主机最大漂移、时间回拨处理和高精度舍入/拒绝策略               |
| 序列含义 | 不改当前 `TagValue.sequence` 严格递增语义；新增独立的**传输完整性元数据**作为后续协议候选，不把其冒充 Tag 版本号                                     | 是否需要连续事件游标；是逐源、逐 Tag 还是逐订阅序列域；持久化及重启后是否延续 |
| 流中断   | 连接断开、鉴权过期、重放、不可解释的传输缺口时停止正式报警输入，清理候选基线，重新认证并显式建立新代次                                               | 是否提供持久化事件重放/确认游标；是否允许仅快照恢复实时显示                   |
| 报警事件 | 规则计算与触发/恢复/确认审计统一留在服务端；候选 READY 不等于事件触发                                                                                | 事件 ID、去重键、规则版本、事务顺序、确认权限及不可变审计结构                 |

**重要区别**：当前业务 `sequence` 的跳号不必然是传输缺口。只有上游明确提供了“连续且覆盖所有必需事件”的独立游标契约，才可用期望游标判断缺口。快照可以恢复当前值，但**不能自动重建断流期间已触发又恢复的报警历史**；正式报警如果要求完整历史，须依赖可靠的服务端事件记录与重放或在缺口期间明确标示历史不完整。

## 三、拟议安全不变量

1. 默认关闭正式接入；认证失败、Tag 越权、错误数据源、超龄/未来时间、旧代次、格式错误或已知不可恢复缺口，不得生成正式报警事件。
2. 采集入口验证必须发生在信任边界之内；Core 的 `sourceVerified` 只允许由已核验服务端适配器设置，**不能作为跨网络授权字段**。
3. 会话令牌、订阅代次与数据序列是不同概念；重启或重新认证必须明确划分新会话域，禁止旧订阅回调穿透。
4. 无法证明流完整性时不能声称报警历史完整；前端必须展示可信性或数据质量退化，但不能自行补发确认或改写审计。
5. 不引入 PLC/DCS 写入、浏览器直连、未审核持久化模型或默认开放的网络端口。

## 四、决策门禁

**必须确认，未确认即保持阻塞：**

- D1：可信网关到服务端的认证方式与部署信任边界；身份对应 Tag 白名单。
- D2：可信时间签发方、UTC/毫秒规范化与时钟偏差阈值。
- D3：Tag 业务序列与传输游标是否分离，以及游标连续性、范围与持久化条件。
- D4：断线、数据丢失、背压、重放及重同步是否有可证明的完整性保障。
- D5：报警规则、事件持久化、确认鉴权与不可变审计的最小事务契约。

维护者批准上述契约后，拆分编号 ADR 并更新 SDD；本 RFC 本身不自动成为 Accepted ADR。任何方案不得将未知上游协议行为写成已实现事实。

## 五、后续分批实现与验收计划（均未执行）

1. **先独立定义契约**：对每个决策点给出选项、威胁、兼容性影响及拒绝路径，获得维护者审批后形成正式 ADR。
2. **默认关闭的模拟可信入口**：只支持本机隔离的只读注入；未经授权、Tag 越权、错代次、过期凭据、非法时间与重放需可诊断且不流入报警候选。
3. **序列与重同步专项**：分别验证合法业务序列跳号、明确的连续游标缺口、快照恢复值但不能恢复历史的情形；覆盖取消订阅、资源泄漏和跨重启回放。
4. **服务端报警事务**：独立审查规则版本、触发、恢复、重触发、并发确认和不可变审计；使用已确认隔离 PostgreSQL，不触及生产库。
5. **端到端验收**：React/Vue 同一工程和 Tag 数据表现一致；OIDC 权限、真实网关断流、Windows、Docker、反向代理与完整 `ready` 需分别实测。
