## 2. 已批准决策

| 决策 | 推荐基线                                                                                                                                                    | 安全理由                                                   |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| R-01 | 新增独立工程级 `release:publish` / `release:rollback`；默认拒绝；不从 `version:append`、`version:read` 或 OIDC Groups 自动继承                              | 防止编辑权限升级为生产发布权限                             |
| R-02 | V0.3 仅允许隔离 Lab 设计与验证；生产启用前要求独立审批责任确认；未完成双人审批方案前不开放生产发布                                                          | 将产品权限设计与现场操作授权分离                           |
| R-03 | 首次发布只能针对事务内重新验证的当前已保存 head；要求 `expectedHeadRevision`、`targetRevision`、`expectedReleaseGeneration`；正文和最终 hash 均由服务端读取 | 防止旧预检、客户端正文或伪造摘要成为发布依据               |
| R-04 | 幂等键限定在租户/工程/操作主体/操作类型范围；同键同语义返回同一已提交结果；同键不同语义返回 409；禁止把 Token、Cookie、正文或设备地址放入幂等键             | 避免重复发布、跨工程碰撞及敏感信息进入持久化键             |
| R-05 | 回滚只能选择本工程历史上成功发布过且仍可验证的不可变版本；回滚必须重新执行完整安全门禁并产生新的代次                                                        | 防止“保存过”被误认为“发布过”，并防止旧快照绕过当前安全条件 |
| R-06 | Runtime 只认独立发布指针；事务提交前不可见；发布版本不可用时 fail-closed，不回落到编辑 head 或模拟正常数据                                                  | 保证运行态与编辑态严格隔离                                 |
| R-07 | 成功发布事件、发布指针与 release generation 同一 PostgreSQL 事务提交；失败不得留下孤立事件或半更新指针；失败/拒绝审计另行定义固定安全字段与保留策略         | 保证发布状态与审计事实原子一致                             |
| R-08 | 发布前重新验证 Tag 绑定、数据源质量、Runtime/资源兼容性及只读工业策略；任一门禁无法证明安全即拒绝；绝不通过发布流程触发设备写入                             | 保持工业安全 fail-closed                                   |

## 3. 已批准的协议约束方向

### 3.1 发布

候选命令仍仅作为后续设计输入：

`POST /api/v1/projects/:projectId/releases`

请求只携带受控 CAS 与幂等字段，不携带工程正文、可信主体、租户 ID 或权威 hash。

服务端必须在事务内重新验证：

1. 可信会话与工程级 `release:publish` 权限。
2. 工程租户归属。
3. `headRevision === expectedHeadRevision === targetRevision`。
4. `releaseGeneration === expectedReleaseGeneration`。
5. 数据库中的不可变快照及 SHA-256 完整性。
6. 当前版本静态发布预检。
7. 后续批准的 Runtime、Tag、数据源和工业安全门禁。
8. 幂等请求是否已经产生成功事件。

任何门禁失败均不得推进发布代次。

### 3.2 回滚

候选命令：

`POST /api/v1/projects/:projectId/releases/rollback`

目标只能来自本工程成功发布事件引用的历史版本。

回滚：

- 不修改 `headRevision`。
- 不修改 IndexedDB 草稿。
- 不修改历史版本正文。
- 不改写旧发布事件。
- 必须使用新的 `releaseGeneration`。
- 必须重新执行当前适用的完整安全门禁。
- 失败时保留当前已发布指针。

### 3.3 Runtime

Runtime 后续只读：

- 当前发布指针；
- 指针引用的不可变快照；
- 与该快照匹配的内容摘要。

Runtime 不得：

- 从 `headRevision` 推断运行版本；
- 加载浏览器草稿；
- 采用未提交的发布状态；
- 因发布版本不可用而静默切换到编辑版本；
- 将 `BAD/STALE` 数据伪装成正常质量；
- 触发 PLC/DCS 写入。

## 4. 已批准的数据一致性约束

正式 Schema 实施前至少验证：

- `tenantId + projectId` 的工程闭包。
- 发布状态每工程最多一条。
- 发布事件 generation 每工程唯一且单调。
- 当前指针与最后成功事件保持一致。
- 事件目标必须引用不可变工程版本。
- 发布/回滚不会修改编辑 head。
- 旧 generation 即使目标 revision 恢复，也不能重新提交（ABA 防护）。
- 失败事务不能留下孤立事件。
- 所有 Prisma 模型、字段、索引和约束均具备中文注释。
- 不修改任何已经应用的 Prisma migration。

## 5. Accepted 后的实施与验收顺序

在 ADR-0069 Accepted 之后，按以下顺序进入实现：

### B：权限与 Schema

隔离 `adui_scada_test`：

1. 首次迁移。
2. 二次迁移。
3. 新表/字段/索引中文注释检查。
4. 默认拒绝发布权限。
5. 跨租户访问拒绝。
6. 旧工程保存流程回归。

### C：发布事务

真实 PostgreSQL 双会话验证：

- CAS 冲突。
- ABA。
- 同幂等键重复。
- 同键不同语义。
- 撤权后提交。
- 快照摘要篡改。
- 事件写入失败。
- 指针写入失败。
- 死锁/事务超时/断连。
- 失败后旧指针保持可验证。

### D：只读 Runtime

React/Vue 双端：

- 未发布状态。
- 已发布快照。
- 发布指针切换。
- 快照损坏。
- Tag `BAD/STALE`。
- Runtime 断连。
- 服务端暂不可用。
- 绝不回落到编辑 head。

### E：回滚

验证：

- 仅允许历史成功发布版本。
- 跨租户拒绝。
- 未发布版本拒绝。
- 当前代次 CAS。
- ABA。
- 并发发布/回滚。
- 回滚后编辑 head 与草稿保持不变。

### F：生产安全评审

只在前述全部通过后开展现场只读安全评审。

**本阶段仍不包含 PLC/DCS 写入许可。**
